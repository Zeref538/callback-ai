Interview practice agent

callback-ai

Nemotron 3 Super · 12-question budget

Say "I improved performance" in a real interview and the next question is: by how much, and how did you know? That follow-up is where interviews are decided, and a list of practice questions never asks it. This interviewer reads your answer, decides whether it was specific enough, and asks again when it wasn't. Every score in the debrief quotes your own words.

An LLM agent that turns a job post into weighted competencies, spends a fixed 12-question budget on the ones it is least sure about, probes when an answer's coverage score falls under the interviewer's threshold, and rejects any score whose evidence quote is not a verbatim substring of the transcript.

    Ranking well is not the same as scoring well

    Rank agreement only asks whether the order is right. The chart shows what it hides: the agent treats a decent answer almost like a bad one. In a real session that means more follow-ups than a person would ask, and a debrief that sounds harsher than it should for a middling answer. I am reporting it because 0.90 alone would make it look better than it is.

    Spearman ρ is rank-only, so it cannot see calibration. Human scores 3 to 6 all map to 0.2 or 0.3 coverage, below every interviewer's probe threshold except Nova's 0.3. The practical effect is extra probes on mid-quality answers and harsh per-skill scores in the debrief. A calibration metric (mean absolute error against the human score) would expose this directly and is not in the eval set yet.

    The first numbers were measured on a model that no longer exists

    The Llama column is from July 2026. NVIDIA retired that model on 26 August, so those numbers now describe nothing you can run. The Nemotron columns are the live app's model, run twice on the same answers. Grading also stopped being perfectly repeatable: Llama gave the same score five times out of five, Nemotron gave a 9.2 among its 10s. That spread, 0.32 and 0.33 points, is well inside the target, but it is not zero.

    02The premise

    Interviews are decided by the second question

    Static question banks cannot condition on the answer they just got

    Most interview practice is a list: here is a question, type an answer, here is the next question. The list does not care what you said. A real interviewer does. When you say "we made it faster", they ask how much faster, and that is the moment a prepared answer falls apart.

    So the useful thing to practise is not the first answer. It is being pushed on it. That needs an interviewer that reads the answer, notices what is missing, and asks about exactly that.

    A question bank is a fixed sequence, so it cannot condition on the answer it just received. The signal an interviewer acts on (a missing metric, an unowned "we", a vague quantifier) only exists after the answer, which makes the follow-up a decision, not a lookup.

    That decision is what the agent makes each turn: probe the same competency, move on, or give up on it, from the answer's coverage score and the interviewer's threshold.

    03The loop

    The model judges the answer. Plain code makes every decision after that.

    One LLM judgement per turn, deterministic policy around it

    Every turn, the model does one job: read your answer and say how complete it was, with a quote from it as proof. Whether to follow up, which skill to ask about next, and when to stop are all decided by ordinary code, the same way every time.

    session_engine.py re-reads the session state each turn and calls one scoring tool. probe_policy.decide and budget_allocator.allocate_next_competency are pure functions of that state, so a transcript replays to the same sequence of decisions (NFR-5).

    Left to the model

    • Which skills a job post is hiring for, and their weights
    • How complete an answer is (0 to 1), with a quote
    • The wording of each question and follow-up

    Enforced in code

    • Follow up or move on: score against a fixed threshold
    • At most one follow-up per skill, four questions per skill
    • 12 questions, never more
    • The quote must appear word for word in your answer

    The three interviewers only differ in how hard they push. Nova follows up below 0.30, Ellis below 0.45, Kade below 0.60. None of them changes how an answer is scored, so a friendlier interviewer asks softer questions but does not mark more generously.

    04The evidence gate

    No quote, no score

    A substring check, not a second model, decides whether a score is grounded

    A model asked to grade an answer will happily praise things you never said. So every score has to come with a quote from your answer, and the code checks that the quote is really there, word for word. If it isn't, the score is thrown away and the model tries again once. If the second try fails too, the score is shown as low confidence instead of being trusted.

    evidence_gate.quote_is_supported lowercases both strings, collapses whitespace and tests containment. A failure increments one shared rejection counter, regenerates once, then returns the result flagged low_confidence rather than looping, which protects the per-answer latency budget. 

    def quote_is_supported(quote, transcript):
    if not quote:
        return False
    return _normalize(quote) in _normalize(transcript)

    It is deliberately dumb. A second model asked "is this grounded?" can be talked into yes. A substring test cannot. The same gate guards the scores during the interview and the final debrief, so the debrief cannot cite anything the live scores could not.

    05The budget

    Twelve questions, spent where it knows least

    Coverage first, then weight × uncertainty, and why the order matters

    A 12-question interview cannot ask about everything twice. So after each answer the agent updates how sure it is about that skill, and picks the next skill by two things: how much the job cares about it, and how unsure it still is. The live demo at the top is exactly this code.

    Each competency keeps an exponential moving average of its coverage scores (α = 0.6, prior 0.5). Priority is weight × (1 − EMA). The allocator takes the highest priority among competencies asked fewer than four times, with ties broken by rubric order so the choice is deterministic.

    The first version never asked about half the job

    Ranking only by weight × uncertainty has a trap. A weak answer makes that skill more uncertain, which makes it the top priority again, which gets another weak answer. The budget collapsed onto the first few skills and the rest were never asked about at all, so the debrief had nothing to score them on.

    The fix was to put coverage first: any skill not yet asked about outranks every skill that has been. Only after each skill has had one question does the budget follow uncertainty. 

    return max(eligible, key=lambda name: (eligible[name].asked_count == 0,
                                       eligible[name].priority))
    06What broke

    Five times it looked fine and wasn't

    Failures found in production, not in tests

    A health check that said "ok" for a month while every interview failed

    NVIDIA retired Llama 3.1 8B on 26 August 2026. From then on every interview on the live site failed with a 502, because NVIDIA answered 410 Gone. The health check kept saying ok the whole time, because it only checks that the server is up and never calls the model. Most other models on NVIDIA's list now answered 404.

    A replacement model that copied the example instead of filling it in

    Llama 3.2 11B was the first replacement. It returned JSON with single quotes and copied the schema's placeholder values on 3 of 3 resume parses, so any interview started with a resume failed. Nemotron 3 Super parsed the same resume correctly 3 of 3 times. It is slower: about 23 seconds to start and 8 to 25 seconds per answer.

    One scoring call in ten came back "overloaded"

    NVIDIA's free tier answered about 1 in 10 scoring calls with 503 Service temporarily overloaded, and each one failed the visitor's answer. Server errors are now retried after 1 second and then 2. Timeouts and client errors are not retried, because trying again would not change the answer.

    The answer box was emptied before the answer was sent

    The page cleared the text box as soon as you pressed send, before the server replied. Any failed request silently destroyed a paragraph someone had just typed. The text now stays until the server confirms it, and comes back with a retry prompt if it fails.

    A portfolio link could point the server at itself

    The app fetches your portfolio page to read it. Nothing stopped that link from being a private address, so a visitor could make the server request pages on its own network. It now resolves the address first and refuses anything that is not public, follows redirects one at a time so each hop is checked, and stops reading after 2 MB.

    07What it cannot do

    Small test sets, one server, and a harsh middle

    Known limits of the evaluation and the deployment

    • The test sets are small. The ranking check uses 10 answers; the plan calls for 20. The follow-up check uses 4: two vague, two specific. "4 of 4" is two runs of two, not a rate you can trust to two decimals.
    • It scores middling answers too low. See the chart in section 01. Nothing in the eval measures calibration yet.
    • Two numbers in the plan are not measured. How often the evidence gate rejects a score, and how uneven the budget really gets, are logged in every session but not yet summarised over real sessions.
    • A restart ends every interview in progress. Sessions live in the server's memory, so the free host restarting drops them. The page warns before you leave, but it cannot save you from the server.
    • Sessions are in process memory on a single worker (WEB_CONCURRENCY=1). A restart drops in-flight sessions; scaling out needs shared storage such as Redis.
    • The health check still does not call the model. The failure in section 06 would still go unnoticed by it.
    • Portfolio reading is best effort. Sites that build their page with JavaScript come back empty, and the interview falls back to the resume.
    08Reproduce it

    Run it yourself

    Try it without installing anything

    The live app needs no account. Paste a job post, pick an interviewer, and answer by typing or by voice.

    Run it offline, no key

    A built-in mock model answers every prompt with simple rules, so the whole app and all 105 tests run without an API key. 

    git clone https://github.com/Zeref538/callback-ai && cd callback-ai
pip install -e ".[dev]"
python -m pytest -q                                  # 105 tests, no key needed
CALLBACK_AI_PROVIDER=mock python -m callback_ai.server   # then open localhost:8000

    Re-run the numbers on this page

    Needs a free NVIDIA key from build.nvidia.com in .env. One run takes about two and a half minutes. 

    NIM_MODEL=nvidia/nemotron-3-super-120b-a12b python -m eval.run_all nemotron-run3
python docs/build_site.py          # rebuilds this page from eval/results/

    Stack: Python, FastAPI, NVIDIA NIM (Nemotron 3 Super), Microsoft neural voices via edge-tts, plain HTML and CSS on Netlify, the API on Render, optional accounts on Firebase. The raw results are in eval/results/.
